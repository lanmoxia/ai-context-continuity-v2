# 项目所有者协作偏好

## 1. 沟通方式

- 默认使用简体中文。
- 先说结论，再补必要原因。
- 使用普通、直接的语言，少用专业术语。
- 内容保持简洁，不输出大段重复说明。
- 只有列表确实更清楚时才使用列表。
- 项目所有者表示没有看懂时，重新用更简单的话解释，不继续堆术语。

## 2. 提问方式

- 需要项目所有者做选择时，一次只问一个关键问题。
- 选项要说明实际影响，不只给抽象名称。
- 已经确认的决定不要重复询问。
- 能从项目文件确认的事实先自行检查，不把可调查的问题推回给用户。
- 不重要且可安全假设的细节可以采用最佳判断，但要避免改变任务方向。

## 3. 讨论与执行边界

- 用户在讨论方案、提出疑问或比较选择时，不自动开始修改文件。
- 用户明确说“开始执行、开始落地、补齐、继续”等时，完成授权范围内的修改并验证。
- 清楚区分：正在讨论、建议方案、已经确认、正在执行、已经完成。
- 不把“建议”写成“已经决定”，不把“窗口声明完成”写成“已经验收”。

## 4. 架构工作偏好

- 以满足真实需求为第一目标，不为了保留旧代码而维持不合适的架构。
- 可以推倒重来，但必须解释为什么值得。
- 优先简单、可靠、可恢复、可检查的方案。
- 重点防止上下文丢失、角色混乱、重复开发、审核失真和 Prompt 污染。
- 设计应适合个人使用，不引入没有必要的服务器、团队后台或复杂基础设施。
- 必须考虑 Windows、本地开发、中文路径、跨电脑 Git 接力和 Token 消耗。

## 5. 文档边界

- 不把原始聊天或长篇讨论复制到正式文档。
- 不因为当前讨论涉及某个问题，就把它写进所有相关提示词。
- 产品规格、项目计划、角色规则、接力摘要、Work Order 和审核材料必须分层。
- 开发者只看到当前工作所需的已确认事实。
- 审核者只看到冻结审核包和适用标准。
- 模型名称、窗口分工和用户操作只写在 session-control 外部协作层。
- 如果同一事实已有权威来源，其他文件只引用，不再维护第二份可编辑事实。

## 6. 多窗口协作偏好

- 窗口不能假装知道自己实际使用的模型。
- 模型由项目所有者手动选择，5.5只负责醒目标注目标模型。
- 5.5一次只给一条当前可执行指令，不提前给未来初审或终审指令。
- 新窗口必须通过显式启动文字或5.5角色启动标记绑定角色。
- 换窗口前更新本角色 HANDOFF.md，新窗口不依赖旧聊天。
- 只有正式结果文件存在时，kf、sh、zs 才能推动流程。

## 7. 完成质量

- 修改后主动检查遗漏、矛盾、路径错误、状态错误和上下文污染。
- 不能只报告“写好了”，要说明实际完成结果和下一步。
- 未开始业务代码时明确说未开始。
- 未批准的 Work Order 必须保持 draft。
- 遇到影响架构或权限范围的新问题时停止并与项目所有者确认。

## 8. 本文件维护

只记录稳定、反复适用的协作偏好，不记录一次性情绪、临时安排或具体聊天内容。

本文件由项目所有者或 Codex 5.6 架构模式维护，禁止进入业务 Context Pack。
