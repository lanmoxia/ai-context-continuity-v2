# 文档地图

本目录按用途隔离，不能把所有文件一起交给 AI。

## `spec/`：产品与技术规格

只保存长期有效的产品事实、架构约束、数据定义和验收标准。

规格处于 `draft` 时只允许架构设计使用；状态变为 `accepted` 后，才允许按当前任务需要进入开发或审核上下文。

## `planning/`：项目管理材料

保存未确认决定、实施顺序和开发任务拆分，供项目所有者和架构设计使用。

这些文件包含“为什么这样设计”“还有什么没确认”等前置信息，默认禁止进入实现、审核、恢复和最终验收上下文。

## `work-orders/`：独立开发工作单

每个目录只描述一个可开发、可测试、可审核的任务。Work Order 处于 draft 时只能用于架构确认；批准后才允许进入 implementation Context Pack。

## `document-registry.json`：唯一准入表

记录每份文档的类别、状态和允许用途。上下文生成器采用默认拒绝：文件没有登记、状态不允许或不在当前用途白名单中，就不能进入上下文包。

## 禁止做法

- 不允许使用“阅读整个项目”“阅读全部 docs”作为启动要求。
- 不把聊天记录或讨论摘要复制进规格文档。
- 不把未来计划、被否决方案或未确认选择交给实现或审核任务。
- 不因某个问题正在讨论，就把它写进所有相关文件。
- 不让同一事实同时存在于多份可编辑文档。

## 正确入口

每个工作任务应获得一个独立上下文包。上下文包只包含：

1. 当前任务必须遵守的已确认规格。
2. 当前工作单。
3. 当前进度或审核证据。
4. 明确列出的按需参考文件。

上下文包不包含角色提示词。角色提示词与事实材料分开管理。
