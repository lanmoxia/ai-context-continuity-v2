# 架构决定

以下决定已由项目所有者确认。日期：2026-07-17。

## D-001：工具与业务项目分离

- 状态：accepted
- 决定：V2 是一个独立工具；业务项目只增加 `.continuity/` 数据目录。
- 原因：避免老项目那种复制大量脚本和文档、升级困难、文件冲突的问题。

## D-002：JSON 保存事实，Markdown 只做阅读页

- 状态：accepted
- 决定：同一状态不允许 JSON 和 Markdown 分别手工维护。
- 原因：消除多份文件不同步。

## D-003：单一写入入口

- 状态：accepted
- 决定：核心状态只能由本地 CLI 写入；AI 不直接改 `current.json`。
- 原因：统一校验、编号、锁和原子写入。

## D-004：第一版只有一个 active 主任务

- 状态：accepted
- 决定：同一业务项目一次只允许一个正在改代码的 Task。
- 原因：降低变更归属、审核基线和接力状态混乱。
- 说明：开发、初审、中审、终审仍可由多个模型和窗口完成，不等于只用一个模型。

## D-005：检查点、接力和审核包分开

- 状态：accepted
- 决定：Checkpoint 用于工作中恢复，Handoff 用于换窗口，Review Pack 用于冻结审核输入。
- 原因：三者生命周期和可信度不同，混用会造成“保存一次进度就触发审核”等问题。

## D-006：Python 实现，无常驻服务

- 状态：accepted
- 决定：第一版使用 Python 包和本地 CLI，不建设数据库或后台服务。
- 原因：适合 Windows 本地运行，开发和测试成本较低，后续仍可封装为可执行程序。

## D-007：Git 分级使用

- 状态：accepted
- 决定：普通接力不强制 Git；正式代码审核要求 Git。
- 原因：接力可以只依赖文件状态，但审核新鲜度必须有可靠代码基线。

## D-008：第一版不控制 AI 客户端

- 状态：accepted
- 决定：工具只生成文件和简短启动入口，不负责打开窗口、切换模型或发送提示词。
- 原因：先解决可靠接力，再处理平台差异和自动化。

## D-009：上下文默认拒绝

- 状态：accepted
- 决定：任何文档默认不能进入运行时上下文，必须由注册表和当前 purpose 同时允许。
- 原因：阻止聊天前置、路线图、其他任务和未确认决定污染当前工作。

## D-010：短时锁与长期租约分开

- 状态：accepted
- 决定：文件锁保护一次状态写入，Writer Lease 保护跨窗口开发时段。
- 原因：一次 CLI 写入结束后，仍需防止第二个开发窗口同时修改源码。

## D-011：检查证据绑定源码指纹

- 状态：accepted
- 决定：检查结果必须记录 Source Fingerprint；源码变化后自动失效。
- 原因：避免旧测试结果被用于新代码。

## D-012：不自动永久删除

- 状态：accepted
- 决定：第一版归档只移动记录，不永久删除。
- 原因：优先保证可恢复性，空间优化以后再处理。

## D-013：阶段审核与总体验收

- 状态：accepted
- 决定：普通 Stage 需要两道 Review Gate；高风险 Stage 增加第三道；所有 Stage 完成后，Task 必须再做一次总体验收。
- 原因：控制重复审核成本，同时保留大任务的集成质量门槛。

## D-014：全部可恢复数据进入 Git

- 状态：accepted
- 决定：Checkpoint、Handoff、Context Pack、Evidence、Review Pack 和归档全部提交 Git；只排除无法跨电脑使用的锁、pending 事务、临时文件和缓存。
- 原因：支持在不同电脑完整恢复开发现场。

## D-015：跨电脑发布自动化

- 状态：accepted
- 决定：显式执行 transfer publish 后，无二次确认地自动生成接力、提交并 push；只提交 Work Order 允许路径和 `.continuity` 可恢复数据。
- 原因：减少跨电脑切换步骤，同时避免无关修改混入。

## D-016：远端同步只允许 fast-forward

- 状态：accepted
- 决定：恢复时自动 fetch，只执行安全 fast-forward；远端分叉、冲突或远端领先无法快进时停止。
- 原因：不自动 rebase、merge 或强推代码历史。

## D-017：审核使用独立副本

- 状态：accepted
- 决定：审核在隔离的 Git worktree 或临时克隆中进行；审核修改只保存为 Suggested Patch，不自动合并正式开发目录。
- 原因：允许充分测试和验证，同时不污染开发现场。

## D-018：Checkpoint 按完成步骤保存

- 状态：accepted
- 决定：每完成一个明确小步骤保存 Checkpoint；重大修改前和换窗口前强制保存。
- 原因：检查点保存可靠事实，不按固定时间机械记录半完成状态。

## D-019：Task 分支和主分支合并

- 状态：accepted
- 决定：每个 Task 使用独立分支；总体验收后生成合并计划，由项目所有者确认；主分支使用 squash 单提交；随后创建归档标签并删除 Task 分支。
- 原因：兼顾过程追溯和主分支整洁。

## D-020：风险和质量门槛

- 状态：accepted
- 决定：Work Order 先标风险，工具只能自动提高；严重和高风险 Finding 必须修复，中等问题需修复或明确接受，轻微建议不阻止；required checks 未全部通过时禁止生成正式 Review Pack。
- 原因：建立统一质量底线，避免审核者自行改变通过标准。
