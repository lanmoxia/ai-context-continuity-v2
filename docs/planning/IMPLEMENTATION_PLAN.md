# 实施计划

## 阶段 0：确认需求和架构

目标：确认项目边界，避免直接开始写脚本后再次返工。

- 确认需求文档。
- 确认目录结构。
- 确认状态、任务、阶段、检查点、接力和审核包之间的关系。
- 确认 Context Pack、Evidence、Source Fingerprint 和 Writer Lease。
- 确认工具仓库与业务项目状态目录分离。
- 确认第一版使用 Python、JSON、Markdown 和 Git。

完成标准：需求和架构得到人工确认。

## 阶段 1：建立工程骨架和可靠存储

目标：先保证状态不会写乱或写坏。

- 建立 Python 包、命令入口和测试结构。
- 定义 JSON Schema 和状态转换。
- 实现配置校验、文档注册表和数据版本检查。
- 实现项目初始化。
- 实现原子写入、状态版本、pending 事务和独占锁。
- 实现路径边界检查。
- 实现 JSON 到 Markdown 的统一生成。

完成标准：并发、断电模拟和非法状态不会破坏最后一份有效状态。

## 阶段 2：实现最小接力功能

目标：先证明新窗口可以可靠接力。

- 创建和读取当前任务。
- 创建阶段和工作检查点。
- 实现 Source Fingerprint 和 Writer Lease。
- 生成工作接力记录。
- 按 purpose 生成最小 Context Pack。
- 新窗口恢复检查。

完成标准：一个任务可以跨两个窗口继续，且不依赖旧聊天。

## 阶段 3：实现阶段与审核包

目标：让一个大任务可以分阶段开发和审核。

- 创建阶段任务。
- 生成阶段完成接力。
- 收集 Git 代码变化。
- 运行已批准检查并生成绑定源码指纹的 Evidence。
- 生成带哈希的审核包。
- 修改后自动让旧审核失效。
- 实现普通 Stage 两道 Gate、高风险 Stage 三道 Gate。
- 实现隔离审核副本和 Suggested Patch。

完成标准：审核结论只能用于它实际审核过的代码和测试结果。

## 阶段 4：实现 Git transfer 与总体验收

目标：支持跨电脑无损接力，并保证进入主分支的代码完成总体验收。

- 自动创建 Task 分支。
- 实现限定范围的 `transfer publish` 和 fast-forward-only `resume`。
- 实现 Task Final Review Pack 和 TASK-FINAL Gate。
- 实现需人工确认的 squash Merge Plan。
- 创建归档标签后删除 Task 分支。

完成标准：两台电脑可以通过远端 Git 恢复同一现场，未经总体验收和 Merge Plan 确认不能修改主分支。

## 阶段 5：实现健康检查和恢复

目标：能够发现状态错误和未完成写入。

- 检查状态文件格式。
- 检查任务、接力和审核编号是否一致。
- 检查路径是否越界。
- 检查是否存在疑似密钥。
- 检查是否有两个窗口同时写入。
- 检查过期写入租约和 Context Pack 污染。
- 从最后有效检查点或接力恢复。
- 模拟窗口在写入各步骤中异常退出。
- 实现 Schema 迁移 dry-run 和完成任务归档。

完成标准：常见错误能够被发现，并给出明确恢复建议。

## 阶段 6：真实项目演练

目标：验证 V2 能在真实项目中使用。

- 模拟开发窗口达到上下文上限。
- 切换新窗口继续开发。
- 完成至少两轮独立审核和修改后重审。
- 检查 token 使用和重复读取情况。
- 验证项目管理文档和其他任务历史没有进入运行时 Context Pack。
- 在两台隔离工作目录之间完成 publish/resume。
- 完成隔离审核、Suggested Patch、Task Final Review、squash 和归档标签流程。

完成标准：完整流程通过，旧聊天记录不可用时仍能继续工作。
