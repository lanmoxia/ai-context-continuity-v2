# 项目需求

## 1. 项目要解决的问题

AI 编程任务经常无法在一个会话窗口内完成。窗口上下文不足、客户端异常或人工切换窗口后，新窗口容易出现以下问题：

- 不清楚项目长期规则。
- 不知道当前任务做到哪里。
- 重复已经完成的工作。
- 把没有验证的内容当成已经完成。
- 需要重新读取大量文件，浪费 token。
- 开发结果在多个模型之间传递时发生遗漏。

本项目需要让新窗口通过少量、可信的项目文件恢复工作。

## 2. 核心目标

### 2.1 长期规则

每个项目有一个明确的长期规则入口。只有在项目文档注册表中登记并确认的规则文件，才允许进入运行时 Context Pack。

### 2.2 长任务分阶段

一个大任务可以拆成多个阶段。每个阶段可以跨越多个开发窗口，不要求一个窗口一次完成。

每次具体开发使用独立 Work Order，只包含当前阶段的目标、允许范围、禁止范围、输入、输出和验收检查。Work Order 不包含架构讨论过程、未来路线图或其他任务信息。

### 2.3 窗口接力

窗口切换前应生成一份接力记录，至少包含：

- 当前任务和当前阶段。
- 本窗口已经完成的工作。
- 尚未完成的工作。
- 修改过的文件。
- 已运行的测试及结果。
- 当前风险或不确定内容。
- 下一个窗口应执行的第一步。

接力记录必须保存为结构化数据，并生成方便人和 AI 阅读的 Markdown。Markdown 不是第二份状态来源。

### 2.4 中断恢复

正常换窗口前生成正式接力。工作过程中还应保存轻量检查点。

如果窗口意外中断，新窗口从最近一次有效检查点继续。系统必须明确提示“检查点之后的聊天内容可能未保存”，不能把未知内容假装成已完成。

### 2.5 分阶段审核

开发过程中可以保存工作接力，但不需要每次换窗口都审核。一个完整阶段完成后，才生成正式审核材料。

一个 Stage 可以配置多道通用 Review Gate。所有必需 Gate 必须针对同一个 fresh Review Pack 通过，Stage 才能批准。具体执行者由外部流程映射，核心数据不写死模型或客户端名称。

普通 Stage 使用两道 Gate，高风险 Stage 增加第三道。所有 Stage 通过后必须生成 Task Final Review Pack，并通过独立总体验收，才能准备合并主分支。

### 2.6 审核可信

审核结果必须对应明确的任务版本、代码变化和测试结果。任务在审核后又发生变化时，旧审核自动失效。

代码、任务标准、接力和测试证据都必须带同一份源码指纹。指纹不同的材料不能组合成正式审核包。

### 2.7 控制上下文大小

系统为每项工作生成带 manifest 的最小上下文包。manifest 精确列出必读文件、按需文件、哈希和大小预算。

默认拒绝未登记文档。聊天记录、项目管理材料、未确认决定、其他任务记录、历史接力和完整测试输出不得自动进入上下文包。

启动材料只保存摘要和文件路径，不复制源码、完整 diff 或完整测试日志。

### 2.8 人工可控

第一版允许用户在不同客户端之间复制一条简短指令。系统负责把详细内容写入文件，用户不需要反复复制大段提示词。

### 2.9 状态一致

- 任务状态只允许由本地工具更新。
- JSON 保存机器事实，Markdown 由 JSON 自动生成。
- 同一含义不能由多份可编辑文件分别维护。
- 每次状态更新必须有递增版本号。
- 写入中断后必须可以识别未完成事务，并保留上一份有效状态。

### 2.10 任务并发边界

同一项目只允许一个正在改代码的 active 主任务，并且同一时刻只允许一个有效写入租约。

多个只读审核可以针对冻结审核包进行，但审核期间源代码一旦变化，原审核包立即失效。

### 2.11 配置与生命周期

- 上下文预算、文件限制、写入租约、Git 策略和允许执行的检查由项目配置管理。
- 配置必须经过 Schema 校验，不能从任务文本动态生成可执行命令。
- 数据格式升级必须先备份和 dry-run，不兼容版本默认只读。
- 完成任务可以归档，但第一版不自动永久删除记录。

### 2.12 跨电脑接力与 Git

- 每个 Task 使用独立 Git 分支，所有 Stage 在该分支依次完成。
- 所有可恢复数据提交 Git，只排除锁、pending 事务、临时文件和缓存。
- transfer publish 由用户显式启动，随后自动生成接力、commit 并 push，不二次询问。
- 自动提交只包含当前 Work Order 允许路径和 `.continuity` 可恢复数据；发现无关修改时停止。
- transfer resume 自动 fetch，只允许安全 fast-forward；分叉或冲突时停止。
- Task 总体验收后生成 Merge Plan，经项目所有者确认后 squash 为主分支一个提交。
- 合并成功后为 Task 分支最终提交创建归档标签，再删除 Task 分支。

## 3. 安全要求

- 不允许读取或修改项目目录之外的文件。
- 不允许审核窗口修改开发代码。
- 删除、覆盖、安装和外部发布必须受到限制。
- 接力记录和审核材料不得包含密码、密钥或登录凭据。
- 两个窗口不能同时修改同一份核心状态。
- 两个开发窗口不能同时持有有效写入租约。
- 所有文件路径必须在目标项目根目录内；符号链接或路径跳转也不能绕过限制。
- 审核包默认排除二进制文件、超大文件、`.git` 内部文件和疑似敏感信息。
- 未在配置中预先批准的命令不得由工具自动执行。
- 敏感信息扫描同样覆盖任务、接力、检查结果和生成的上下文包。
- 自动 Git 流程禁止 force push、自动 rebase、自动 merge 冲突、自动 stash、reset 和清理无关文件。
- 审核必须使用隔离副本；审核修改只能输出 Suggested Patch，不能直接进入正式开发分支。

## 4. 非功能要求

- 核心工具默认离线运行，不上传项目内容、状态、日志或统计数据。
- 除时间、编号等明确字段外，相同输入必须生成相同内容和哈希。
- `render`、`status`、`doctor` 和 dry-run 操作必须幂等，不修改业务代码。
- 安全状态不明确时采用 fail-closed：停止并说明，不猜测、不自动修复。
- 默认操作只扫描当前 Task 允许路径，不遍历 `.git`、归档、依赖目录或整个磁盘。
- 本地日志采用结构化、可轮转设计，不记录完整密钥、源码正文或大段检查输出。
- 文本统一使用 UTF-8，并支持 Windows 中文、空格和长路径场景。

项目所有者批准的检查命令可能自行访问网络；工具必须明确区分“核心工具行为”和“外部检查命令行为”。

## 5. 核心工具 MVP 边界

- 不自动选择或切换模型。
- 不自动打开和控制不同 AI 客户端。
- 客户端、角色和模型适配属于独立扩展层，不进入核心工具。
- 不支持多个开发任务同时修改同一项目。
- 不建设服务器、团队账号或在线管理后台。
- 不引入向量数据库。
- 不承诺恢复尚未写入检查点的聊天内容。

## 6. 第一版验收标准

- 长任务可以跨至少两个新窗口继续。
- 新窗口只读当前 Context Pack 即可说明现场。
- 窗口异常退出后，新窗口可以恢复到最近检查点，并明确指出可能丢失的区间。
- 已完成、未完成和未验证内容能够明确区分。
- 阶段审核只包含当前阶段所需材料。
- 审核后修改代码会让旧审核失效。
- 中途写入失败不会破坏上一次有效接力。
- 接力和审核文件大小保持可控，不再复制全部历史日志。
- 两个窗口同时写状态时，一个成功，另一个得到明确的占用提示。
- 两个窗口申请开发写入权时，只能有一个获得有效租约。
- 路径越界和疑似密钥进入审核包时会被拒绝。
- 项目管理文档中即使存在冲突文字，也不能进入实现或审核 Context Pack。
- 检查证据与源码指纹不一致时不能进入正式审核包。
- 相同状态重复 render 不产生无意义变更。
- 未运行外部检查命令时，核心流程不需要网络连接。
- 公司电脑生成 transfer 后，家里电脑仅凭远端 Git 数据可以恢复到同一可靠现场。
- 自动提交不会包含 Work Order 范围外的修改。
- 普通 Stage 两道审核、高风险 Stage 三道审核和 Task 总体验收均可被状态机强制执行。
- required checks 未全部通过时不能生成正式 Review Pack。
